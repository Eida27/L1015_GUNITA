#### Important (Should Fix)

- **I1 — Preserve an account-management path after its reports disappear.** `src/components/moderation/admin-view.tsx:220` fetches reports even for the accounts screen; `src/server/moderation/service.ts:210–221` also derives the accounts API exclusively from `inspectReports`, whose query excludes expired thoughts (`src/server/moderation/reports.ts:100–103`). Suspend an author, then delete their last reported thought or let it expire: the account remains suspended, but vanishes from both account discovery paths, and the only unsuspend controls are on those report cards. The audit UI also provides no usable account identifier. The API can unsuspend only if an operator retained an ID elsewhere, which does not fulfill the requested admin-console lifecycle. Provide a guarded, minimally identifying account listing/retrieval path that keeps suspended accounts manageable independently of live reports, wire the accounts UI to it, and test suspend → last report deletion/expiry → UI unsuspend without retaining deleted content.

- **I2 — Expose enough safe linkage to review moderation history.** `src/server/moderation/service.ts:202` selects only audit event ID, action, subject kind, reason, changed status and time. `src/lib/moderation-contract.ts:78–117` has no subject or actor reference, and `src/components/moderation/admin-view.tsx:304–305` renders only the action/reason/status/time. Thus two suspensions or hides cannot be associated with their accounts/thoughts or with the responsible administrator anywhere in this history interface, even while all subjects still exist. The database records linkage, but the requested review-history/admin-audit workflow cannot use it. Add narrowly allowlisted nullable subject and actor references or safe labels to the guarded history DTO/UI, preserving existing deletion unlinking and excluding body/email copies. Verify two different subjects/admins are distinguishable and deleted linkage remains absent.

- **I3 — Detect the authentication cookie, not any cookie, when choosing guest reporting.** `src/server/moderation/reports.ts:46–48` treats every nonempty `Cookie` header as a member session and calls `requireVerifiedMember`. A legitimate guest carrying an unrelated cookie (for example `theme=dark`) therefore gets 401 after consuming both verification and report-attempt budget, while the same request with no cookies succeeds. Cookie presence does not establish membership; this breaks the explicitly permitted guest-report path. Check for the actual supported session-cookie name using the auth library's parser, retaining the intended rejection of invalid/revoked member credentials, and add a guest-with-unrelated-cookie regression alongside the genuine member guard cases. The unchanged guard confirms a request without an authenticated session throws `UNAUTHENTICATED` (`src/server/auth/guards.ts:41–47`).
